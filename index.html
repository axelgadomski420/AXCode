Jeden plik.
Cała aplikacja.

AXCode to hipotetyczny, produkcyjnie zaprojektowany język do tworzenia aplikacji mobilnych, webowych i desktopowych. Jeden plik .ax opisuje interfejs, stan, dane, nawigację, dostępność, offline, testy i integracje — bez osobnych plików HTML, CSS i JavaScript.

Filozofia

Aplikacja powinna być czytelna jak opis produktu.

AXCode nie próbuje zastąpić wszystkich języków programowania. Jest językiem warstwy aplikacji: ekranów, stanu, formularzy, nawigacji, danych i testów. Zaawansowany kod natywny pozostaje dostępny przez bridge, ale nie jest wymagany do zbudowania typowej aplikacji.

📄

Jeden ekran = jeden blok

Ekran zawiera własny stan, layout, zdarzenia i nawigację. Nie trzeba skakać między plikiem widoku, plikiem stylów, plikiem stanu i plikiem logiki.

⚡

Reaktywność bez boilerplate’u

Zmiana stanu automatycznie aktualizuje UI. Programista nie pisze ręcznej synchronizacji DOM, listenerów ani cyklu życia komponentu.

🧠

Błędy po ludzku

Kompilator pokazuje problem, przyczynę, pozycję i gotową poprawkę — po polsku i angielsku. Błąd ma uczyć, a nie tylko blokować build.

♿

Dostępność wbudowana

Brak etykiety pola, obrazu bez opisu albo zbyt niski kontrast są wykrywane przed uruchomieniem. AXCode traktuje dostępność jako część semantyki aplikacji.

🔒

Prywatność jako typ

Dane wrażliwe, klucze i tokeny mają jawną klasę przechowywania. Nie można przypadkiem zapisać sekretu w zwykłym lokalnym store.

🚫

Celowo mniejsza powierzchnia

Brak dowolnych makr, dynamicznej ewaluacji, globalnych selektorów CSS i pięciu składni na ten sam problem. Mniej możliwości oznacza mniej błędów.

Składnia

Kod, który można przeczytać bez znajomości frameworka.

Poniższy przykład pokazuje ekran, stan, listę, formularz, nawigację, motyw i zapis lokalny w jednym pliku AXCode.

app.ax 
// AXCode — aplikacja zadań
app "Tasks"
version "1.0.0"
language pl
supports ios android web

theme default
  follows system
  color primary #2563EB
  color background light #F8FAFC
  color background dark #0B1220

data Task
  id Text
  title Text
  done Boolean
  created Date

store tasks local
  list Task
  key "tasks"

screen Home
  title "Moje zadania"

  state newTitle Text = ""

  when screen appears
    load tasks

  column
    padding 20
    gap 16

    text "Moje zadania"
      style title

    form "Nowe zadanie"
      field newTitle
        label "Nowe zadanie"
        required
        min length 1

      submit "Dodaj"
        when valid
          add Task(
            id = newId(),
            title = newTitle,
            done = false,
            created = now()
          ) to tasks

          save tasks
          set newTitle = ""

    list tasks
      empty
        text "Brak zadań"

      item task
        card
          row
            checkbox task.done
              accessibility label "Oznacz jako wykonane"

            text task.title

            button icon "trash"
              accessibility label "Usuń zadanie"
              when tapped
                remove task from tasks
                save tasks
Benchmark

Ile naprawdę można zaoszczędzić?

Poniższe liczby dotyczą referencyjnej aplikacji zadań: logowanie, lista, dodawanie, usuwanie, tryb ciemny, zapis lokalny i responsywny layout. To nie jest marketingowy „zawsze 10× mniej”, lecz realistyczny model redukcji boilerplate’u.

HTML + CSS + JavaScript

Osobne warstwy struktury, wyglądu i logiki. Programista ręcznie aktualizuje DOM, obsługuje zdarzenia, serializuje stan i dba o dostępność.

React Native

Jeden język aplikacji, ale zwykle osobne pliki komponentów, stylów, nawigacji, stanu i warstwy danych. Mocny ekosystem, jednak więcej konfiguracji i abstrakcji.

Jak to tłumaczyć naukowo

  • Redukcja linii nie jest celem samym w sobie. Celem jest redukcja przypadków zmiany, duplikacji i błędów integracji między warstwami.
  • AXCode eliminuje trzy źródła boilerplate’u: ręczną synchronizację UI ze stanem, powtarzalną konfigurację dostępności oraz glue code między danymi, widokiem i nawigacją.
  • Kompilator przenosi błędy z runtime’u do czasu kompilacji. Nieznany ekran, zły typ pola, brak etykiety dostępności albo zapis sekretu w niezabezpieczonym store są wykrywane wcześniej.
  • Nie ma darmowej abstrakcji. AXCode zmniejsza kod aplikacji, ale zwiększa złożoność kompilatora i runtime’u. To świadomy trade-off: złożoność przenosimy z milionów aplikacji do jednego narzędzia.
Kompilator

Jeden front-end. Wiele backendów.

AXCode nie tłumaczy tekstu bezpośrednio na Swift, Kotlin czy JavaScript. Najpierw tworzy neutralną reprezentację aplikacji AXIR, a dopiero potem generuje kod dla platformy.

app.ax │ ▼ Lexer ──► Tokeny, pozycje, komentarze │ ▼ Parser ──► AST + recovery + wiele błędów naraz │ ▼ Type Checker ──► typy, zasięgi, stany, uprawnienia, dostępność │ ▼ AXIR ──► platformowo-neutralny graf aplikacji │ ├──► Optimizer │ • dead code elimination │ • inline komponentów │ • memoizacja stabilnych fragmentów │ • tree shaking │ ├──► iOS Backend ──► Swift + SwiftUI / native runtime ├──► Android Backend ──► Kotlin + Jetpack Compose / native runtime ├──► Web Backend ──► Wasm core + TypeScript glue + DOM renderer ├──► Desktop Backend ──► natywne shelle │ └──► Dev Server • hot reload • live preview • accessibility inspector • device simulator

Hot reload

Zmiana pliku `.ax` tworzy patch AXIR. Runtime stosuje zmianę bez utraty stanu, jeśli typy i struktura danych są zgodne. Przy zmianie niekompatybilnej wykonuje bezpieczny restart ekranu.

Diagnostyka

Każdy błąd ma identyfikator, lokalizację, wyjaśnienie w PL/EN oraz sugerowaną poprawkę. Parser nie zatrzymuje się na pierwszym błędzie — pokazuje wiele problemów jednocześnie.

Web i WebAssembly

Logika aplikacji może być kompilowana do WebAssembly, a cienka warstwa TypeScript obsługuje zdarzenia, nawigację i integrację z przeglądarką. Renderer DOM zapewnia dostępność i SEO.

Podgląd na żywo

Dev server pokazuje ten sam ekran jako iPhone, Android, tablet i desktop, z możliwością symulacji trybu ciemnego, dużego tekstu, redukcji ruchu i czytnika ekranu.

Specyfikacja

Pełna specyfikacja języka AXCode

Poniższa specyfikacja opisuje minimalny, spójny core języka. Rozszerzenia platformowe są opcjonalne i nie psują przenośności podstawowego kodu.

1. Jednostki programu

Podstawowymi jednostkami są app, screen, component, data, store, theme, api i test. Plik `.ax` może zawierać całą aplikację albo jeden moduł.

2. Typy

Wbudowane typy: Text, Number, Boolean, Date, List<T>, Json, File oraz typy opcjonalne z sufiksem ?. Typy własne definiuje się przez data i enum.

3. Stan

state jest lokalny dla ekranu, global state dla aplikacji, a store jest trwały. Store może być local, synced lub encrypted.

4. Zdarzenia

Zdarzenia mają formę when tapped, when changed, when screen appears, when valid i when error. Efekty uboczne są jawne.

5. Listy

Listy UI są deklaratywne: list, item i empty. Nie ma ręcznego renderowania ani kluczy DOM w podstawowym przypadku.

6. Formularze

Formularz posiada walidację deklaratywną: required, min length, max length, type email, type password oraz komunikaty błędów.

7. Nawigacja

Nawigacja jest typowana: go to ScreenName, go back oraz przekazywanie parametrów ekranu. Kompilator wykrywa nieistniejące ekrany i złe typy parametrów.

8. Motywy

Motyw definiuje kolory, promienie, cienie, typografię i tryb jasny/ciemny. Motyw może następować za ustawieniami systemu lub być wymuszony przez aplikację.

9. Animacje

Animacje są ograniczone do przewidywalnych przejść: appear, press, transition i layout. Są automatycznie wyłączane przy reduce motion.

10. API i dane

api opisuje endpointy, metody, typy odpowiedzi i obsługę błędów. store obsługuje offline-first, szyfrowanie i synchronizację.

Plan

Od parsera do produktu.

AXCode nie powstaje jako „cały ekosystem od pierwszego dnia”. Najpierw web renderer i diagnostyka, potem natywne platformy, na końcu narzędzia wizualne i AI.

MVP

0–6 miesięcy

Lexer, parser, AST, type checker, AXIR, web renderer, podstawowe komponenty, hot reload, komunikaty błędów PL/EN i testy. Technologie: Rust, TypeScript, Wasm, Playwright.

1.0

6–14 miesięcy

iOS i Android, nawigacja, formularze, motywy, lokalne dane, eksport projektów Xcode i Android Studio, pełny Language Server oraz stabilne API języka.

2.0

12–24 miesiące

Animacje, offline-first, API, synchronizacja, testy UI, profilowanie wydajności, lokalizacja, integracje systemowe i niezależny audyt bezpieczeństwa.

3.0

18–30 miesięcy

Wizualny edytor, sklep komponentów, współpraca zespołowa, pluginy oraz asystent AI generujący ekrany z opisu — zawsze jako reviewowalny kod AXCode, nie nieznany blob.

Dla recenzentów

Dlaczego to jest wykonalne.

AXCode nie wymaga wynalezienia nowej fizyki. Składa się z dobrze znanych, sprawdzalnych elementów: parsera, systemu typów, IR, generatorów kodu i runtime’u UI.

Teza 1

Redukcja kodu wynika nie z „magii”, lecz z eliminacji trzech powtarzalnych warstw: synchronizacji UI, konfiguracji dostępności i glue code’u danych.

Teza 2

Jeden język aplikacji może kompilować się do wielu platform, jeśli pośrednią reprezentacją jest semantyczny graf UI, a nie konkretny framework.

Teza 3

Jakość języka mierzy się nie liczbą funkcji, lecz liczbą błędów, których nie da się łatwo popełnić. AXCode ogranicza powierzchnię języka świadomie.
